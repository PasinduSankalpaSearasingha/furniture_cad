# Joinery request handoff fix — 18 October 2026

The observed workflow completed Vision, Design and the first Joinery response, then failed when submitting the catalog lookup result to the model. The stored error was `AI_API_ERROR`, with no HTTP status, provider code or parameter. The original provider response was discarded, so its exact rejection cannot be reconstructed from the workflow records.

An offline reproduction identified a request serialization defect in that handoff. Serializing SDK output using bare `model_dump(mode='json')` adds unset fields and Python field names such as `async_`. Those objects are then resent as API input. The gateway now uses the SDK's API serialization, `to_dict(mode='json')`, which uses API field names and omits fields absent from the original response. It retains the complete output sequence, including encrypted reasoning state, assistant phases and tool calls. This follows the [official OpenAI function-calling flow](https://developers.openai.com/api/docs/guides/function-calling) and [reasoning context guidance](https://developers.openai.com/api/docs/guides/reasoning). This defect is a likely cause of the observed rejection; no original provider error body is available to prove that attribution.

Future HTTP errors preserve a small diagnostic object through invocation events, workflow errors and structured logs: HTTP status, provider error type/code, affected request parameter and request ID. Free-text provider errors and request bodies are excluded because they can echo credentials or private design input. HTTP 400 is reported as `AI_BAD_REQUEST`; HTTP 422 as `AI_UNPROCESSABLE_REQUEST`. Existing authentication, model-access, rate-limit and server-error handling remains available. [Official error reference](https://developers.openai.com/api/docs/guides/error-codes).

The new SDK transport regression verifies two consecutive tool rounds, exact replay of API fields, reasoning state and message phases, and absence of opaque state in events. Other added tests verify safe HTTP 400/422/500 diagnostics and that a failed Joinery stage can be retried without regenerating completed Vision/Design checkpoints. These checks use mock HTTP transport, never OpenAI's live endpoint.

Refresh the project and choose **Retry workflow** after the API reloads. The prior generic error remains historical; it is not rewritten as a more specific diagnosis. No paid workflow was automatically retried to validate this patch, so live end-to-end success still requires an explicit retry. Manufacturing verification and review gates remain unchanged.
